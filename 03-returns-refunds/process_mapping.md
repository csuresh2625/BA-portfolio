# As-is and to-be process maps (conceptual)

**As-is (simulated):** Customer return request → manual reason review → warehouse receipt → refund approval → payment processing → customer asks support for status.

**To-be (proposed):** Structured reason intake → return ID and status visibility → warehouse verification → refund queue with aging alert → automated status notification → escalation after 7 days → root-cause reporting.

**Gap:** Inconsistent reason capture and reactive communication. **Control:** Keep refunds subject to payment authorisation and fraud checks.
